# Grinder brief (per-agent, disjoint target lists)

You are one of several parallel recovery grinders in `D:\Prog\simantw_recon` (run every command from that directory with `python`). Read `AGENTS.md`, `docs/factory.md`, `docs/grinder-lessons.md` and `docs/cheap-model-prompt.md` first. Work ONLY on the symbols assigned to you, in the given order; never call `grind.py next` (other agents hold other jobs).

Per target:

1. `python tools/grind.py inspect SYMBOL` → JSON with `working_packet`: masked disassembly with loader bindings, `direct_data_bindings` (exact MAPSYM names, selector slots, addressed segments), `calls`, `basic_blocks`, `compiler_profile` (use its flags as given; never change flags), `unit_context` (the same-object component: its other publics are your neighbours), `reconstruction_rules`, `similar_matched_functions`, `known_families`.
2. Read admitted sources of neighbours and analogues under `src/recovered/` (e.g. the B/R twin of an A/B/R/Y routine, the admitted goStep/Finish*Step unit `src/recovered/wf_tu_simtwo_6EFE_*.c`, admitted members of the same `unit_context`). Reuse their declarations verbatim when the same objects are referenced: same names, types, `near`/`far`, element widths, struct shapes.
3. Write readable C with a semantic block comment at the top into `build/grind/<your-agent-name>/SYMBOL.c`. Self-contained: no `#include`, `#pragma`, assembly, absolute-address casts. `#define` is allowed. Declare externs exactly as the MAPSYM names say (`_Foo` in the packet is `Foo` in C; Pascal-exported names like `MYENUMFUNC` are `far pascal MyEnumFunc`). Never invent a symbol when the packet names one; an unnamed DGROUP operand inside a named public array is `array[index]`, not a private static. Private statics need evidence-backed type and initializer; a static in `_BSS` is only right if the original word is above `_edata` (0xCA60).
4. `python tools/grind.py test SYMBOL build/grind/<agent>/SYMBOL.c` → read `strict_member_result`, `diagnostic` (opcode/register/branch/immediate differences, `first_structural_difference`, `unresolved_member_obligations`) and `aligned_asm`. Revise for an explained reason. Budget: 8 attempts per target, 192 candidates total; do not spend them on guesses.
5. `strict_member_result` CONFIRMED_MEMBER or STRONGLY_SUPPORTED_MEMBER → `python tools/grind.py accept SYMBOL build/grind/<agent>/SYMBOL.c`.
6. Status ESCALATED (automatic body-matched/binding stop) → leave it and move on. Otherwise when stuck after a few explained revisions: `python tools/grind.py block SYMBOL "observed mismatch + evidence" --cause CAUSE --next-experiment "one discriminating experiment"` with CAUSE from: REGISTER_ALLOCATION, LOCAL_FRAME_LAYOUT, EXPRESSION_SHAPE, SEMANTICS_UNKNOWN, FAR_POINTER_TYPE, CALLING_CONVENTION, DATA_LAYOUT, PRIVATE_CONST_LAYOUT, TRANSLATION_UNIT_CONTEXT, STRING_INTRINSIC_IDIOM, FP_MODE.

Do NOT park a job yourself with TRANSLATION_UNIT_CONTEXT, PRIVATE_CONST_LAYOUT or DATA_LAYOUT. In an isolated compile every far object's `mov es,[slot]` shows up as an "unsupported or unresolved target/frame" CONST fixup and as "conflicting private placement constraints CONST": that is EXPECTED, it is not a blocker and it is not a regression. Ignore those messages and keep working on the instruction-level differences (`aligned_asm`, opcode counts, register/branch/immediate differences, frame size). When the body is exact (opcode_matches == opcode_total, candidate_bytes == target_bytes, zero register/branch/stack differences) the factory escalates the job automatically as BODY_MATCHED_BINDING_BLOCKED and the supervisor assembles the unit; a body that is not exact is your work. Only block with REGISTER_ALLOCATION / LOCAL_FRAME_LAYOUT / EXPRESSION_SHAPE / SEMANTICS_UNKNOWN / FAR_POINTER_TYPE / CALLING_CONVENTION after real explained revisions (normally at least four attempts unless the compiler cannot express the shape at all). If you parked a job too early and later find a better hypothesis, you may reopen it once: write a spec JSON {"symbol":"_X","source":"build/grind/<agent>/X.c","compiler":"msc700","flags":<flags from the job's job.json>,"max_candidates":1,"axes":[],"semantic_summary":"...","binding_evidence":["..."],"publics":["_X"]} and run `python tools/topology_retest.py <job-id> build/grind/<agent>/X-spec.json --reason "<what changed>"`; it records the attempt on the same budget.

Hard rules: never edit anything under `tools/`, `layout/`, `src/`, `evidence/`, `build/recovered/`, `docs/`; never run `recovery_workflow.py promote/refresh`, `handoff_validate.py`, `git`. If a tool command fails with a lock message, wait a few seconds and retry. If the compile service reports an error, retry once, then report.

Techniques that worked in this corpus: locals copied from parameters when SI/DI hold them; an explicit result variable for `MOV DX,1` tails; word-indexed arrays (`int` for 2-byte strides, `char` for bytes, 8-byte structs for `SHL 3`); `unsigned` comparisons produce `JA/JB`; far data accessed through `extern ... far` names (each far object gets its own selector slot in order of first use in the source, so write references in the order the code loads ES); `for` loops that compile to `rep stosw`; struct copies to `movsw`; same-segment far calls are ordinary far calls (LINK rewrites them).

At the end, reply with a compact table: symbol, result (ACCEPTED / BLOCKED cause / ESCALATED), attempts used, best opcode match, one-line note. Keep candidate files in place.
