# 5. WINDOW GEOMETRY

**Confidence labels:** VERIFIED means admitted source or unambiguous import/disassembly evidence; INFERRED means the best readable draft or incomplete call path; UNKNOWN means this packet does not settle the behavior. This section records the Win16 host delta. The DOS window-object manager remains the authority for logical object layout and event behavior.

[VERIFIED] DOS `win_Open` writes a requested logical rectangle, calls `win_Recalc`, then draws and stacks the object window; DOS `win_Recalc` resolves four-edge anchors, auto-sizes flagged objects, iterates dependencies, sorts rectangles, and copies object zero's rectangle into the window record (`D:/Prog/simant_recon/src/root/m20E8.c:207-255`; `D:/Prog/simant_recon/src/root/m2505.c:294-343`; `D:/Prog/simant_recon/docs/window-model.md`). The Win16 layer retains those `win_*` objects and adds HWNDs and USER/GDI policy around them (`D:/Prog/simant_recon/docs/cross-version.md`, "The DOS window system").

[VERIFIED] The application frame is created from display metrics, not a fixed pixel rectangle or an INI placement: `x = SM_CXSCREEN/100`, `y = SM_CYSCREEN/100`, `width = 98% of SM_CXSCREEN`, `height = 90% of SM_CYSCREEN - SM_CYICON` (`GetSystemMetrics` indices 0, 1, 12; style `0x02CF0000L`). `InitInstance` then reads its client rectangle and creates separate ribbon and root child windows at `(0,0)` (`src/recovered/tu_simant_01B6_DoUserButtonUpdate_15_reviewed-db9484741a.c:1024-1063`). `InitApplication` registers Root, Generic, and Ribbon classes; all use `MainWndProc`, and their class menu names are null (`src/recovered/tu_simant_01B6_DoUserButtonUpdate_15_reviewed-db9484741a.c:1066-1105`).

[VERIFIED] Panel/window definitions are database objects, not the `.RC` dialog templates. `win_LoadAllWindows` reads the desktop rectangle and chooses display-layout object type 9: for `displayType == 9`, object 7 above 480 desktop pixels or object 5 at/below 480; for `displayType == 10`, object 8 above 480 or object 0 at/below 480; other display types use their own number. It then loads object `0x80` for counts and `0x81` for colors, and calls `win_LoadWindow` for each logical window (`src/recovered/tu_simtwo_C32E_win_ObjAddr_20_reviewed-cf86811e02.c:658-758`).

[INFERRED] `WINMAIN` associates logical window `0x2200` with `ribbonBarWnd`, calls `win_Recalc(0x2200)`, and sizes the bar from the loaded record's `header[6]-header[2]`; the root child receives the remaining client height. On `WM_SIZE` (`0x0005`) for the main frame, `MAINWNDPROC` keeps the bar height, resizes the root child to client-height minus bar-height, updates `screenWidth/screenHeight`, and resizes/redraws the bar (`evidence/recovery/drafts/WINMAIN/8c89fbd1b287.c:172-191`; `evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:349-372`). These two procedures remain open drafts.

[INFERRED] Opening a logical window stores the caller's `left/top/right/bottom` in its bucket and calls `win_Recalc` before creating or moving a child `GenericWindow` HWND. The resulting native child size is `right-left` by `bottom-top` plus frame adjustments. The procedure subtracts `ribbonBarHeight` from the top for non-type-5 records, adds border/caption/frame offsets using `GetSystemMetrics`, tags the HWND with property `INDEX`, and raises/shows it (`evidence/recovery/drafts/win_Open/340a8dee76c6.c:89-230`). No `AdjustWindowRect` import occurs in the port audit; the inspected `win_Open` path adjusts styles manually.

[INFERRED] The client/frame distinction is operational: top-level CreateWindow dimensions are outer dimensions; `GetClientRect` supplies the space used for the ribbon/root children. `win_Open` positions game children within `rootWnd` and applies native border/caption metrics there. Mouse handling translates between client and screen coordinates before hit-testing (`ClientToScreen`, `WindowFromPoint`, `ScreenToClient`); popup placement likewise converts an object anchor to screen then root-client coordinates (`MAINWNDPROC`, `WM_MOUSEMOVE 0x0200`, `evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:778-835`; `win_GetEvent`, `evidence/recovery/drafts/win_GetEvent/bec22cc90795.c:128-181`). The SDL host should keep logical `Rect`s in window-client space and translate event positions only at the host boundary.

[INFERRED] A native resize does trigger logical re-layout for the main edit window: in `WM_SIZE`, the window-0 branch adjusts the stored inner rectangle from the new client width/height, adds a 0x12 vertical allowance, calls `win_Recalc(0)`, and updates the edit. Resizing the frame separately resizes root/bar; resizing `rootWnd` adjusts the edit child. The draft does not establish that every open logical window is recalculated on every frame resize (`evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:301-383`). The DOS `win_Recalc` anchor algorithm is the portable behavior to preserve, not the USER notifications themselves.

[INFERRED] The `WM_MOVE` (`0x0003`) case only calls `UpdateEditIfBufInvalid` in the best draft; it does not write the new native position into a logical window rectangle. Thus native moves are host placement, while `win_Open` owns the requested logical rectangle. Position persistence remains unproven with the open `WINMAIN` (`evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:297-300`; `evidence/recovery/drafts/win_Open/340a8dee76c6.c:99-109`).

[INFERRED] Minimum sizes differ by native layer. `WM_GETMINMAXINFO` (`0x0024`) gives `mainRootWnd` a 100x100 minimum track size. For `rootWnd`, `AdjustWndMinMax` derives minimum track dimensions from system frame/caption metrics plus logical object `0x13`; its maximum size also uses `mem_Size(editBuf) + GlobalCompact(-1)` and a 3/4 memory budget (`evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:568-577`; `evidence/recovery/drafts/AdjustWndMinMax/f875c046b912.c:47-107`). Treat the 100-pixel and Win16 memory/metric formulas as shell policy, not as canonical DOS layout constants.

[INFERRED] No application-level x/y/width/height restoration is visible in `WINMAIN`; startup uses the metric formula above. The observed `GetProfileInt`/`WriteProfileString` calls load and save six options (`autotrack`, `music`, `effects`, `events`, `messages`, `silly`) and eight map plus eight yard user-button assignments, with no placement key in the best draft (`evidence/recovery/drafts/WINMAIN/8c89fbd1b287.c:196-207, 225-234, 263-282`; audit imports only `GETPROFILEINT` and `WRITEPROFILESTRING` for `WINMAIN`). Because `WINMAIN` is not admitted, absence of a hidden placement path is not proven.

[UNKNOWN] This section has not decoded each type-9 database object into its numeric per-window rectangles. The selector and 480-pixel split are verified; the full default logical geometry for each display mode must come from the DOS-authoritative window data before choosing SDL logical-size/scaling policy.

# 7. MENUS / RIBBON / APPLICATION SHELL

[VERIFIED] DOS menu events are dispatched through `ProcMenu` using `ev->message & 0xff`; cases include About (1), new game (3), opening Edit/Map/Yard/Mode/Caste/History/Info (0x11-0x16), yard/plane modes (0x21-0x28), option toggles (0x31+), pause (0x41), and speed (0x43-0x45) (`D:/Prog/simant_recon/src/S11/m35F5.c:89-170`). DOS `main` owns a continuous game/event loop rather than a USER message pump (`D:/Prog/simant_recon/src/root/m15F8.c:64-145`).

[INFERRED] Win16 builds a native `HMENU` at runtime from database object kind 6: top-level titles and item strings become menus; a leading hyphen becomes a separator; `#<resource-id>` rows try a nested popup resource; the result is attached to `mainRootWnd` with `SetMenu` (`evidence/recovery/drafts/InitMenu/c16eb3494632.c:31-130`). `WM_COMMAND` (`0x0111`) routes `0xFDxx` menu IDs to `DoMenuEntry`; its `0xFDA0`-family commands handle close/restore/next/move/size/maximize and related native-window actions (`evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:613-700`). The menu source and dispatcher are drafts, so the exact label-to-DOS-command map remains inferred.

[VERIFIED] The ribbon/bar is a separate child host window, distinct from the frame's attached native menu. `InitInstance` creates `ribbonBarWnd` and `rootWnd` as siblings under `mainRootWnd`; `InitApplication` registers a separate Ribbon class. The inferred `WINMAIN` then maps logical index `0x2200` onto `ribbonBarWnd`. This preserves Maxis's drawable ribbon objects while USER owns the child HWND and its sizing/painting lifecycle (`InitInstance/InitApplication` exact source above; `evidence/recovery/drafts/WINMAIN/8c89fbd1b287.c:172-191` is draft).

[INFERRED] Window switching follows native sibling z-order: logical IDs map to HWNDs, `INDEX` properties recover the logical ID, and `GetTopWindow`/`GetNextWindow` plus `BringWindowToTop` find the visible front window. Opening an already-created window raises it; opening a hidden one moves/shows it. The DOS analogue is the logical window stack (`g_5702[]`, DOS `win_Open`/`win_Close`), so SDL must preserve visibility, front-to-back ordering, and "next window" selection without depending on HWND enumeration (`win_Open` draft; `DoNextWindow` exact Win16 source in `src/recovered/tu_simant_01B6_DoUserButtonUpdate_15_reviewed-db9484741a.c:846-860`; DOS `m20E8.c:207-255`).

[INFERRED] Focus and mouse capture are used to keep drag/button events routed to the active child after the pointer leaves it. `WM_LBUTTONDOWN` (`0x0201`) acquires capture; button-up releases it; `win_GetEvent` uses the capture window or falls back to the top visible child, then converts cursor coordinates to that child's client space (`evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:837-858`; `evidence/recovery/drafts/win_GetEvent/bec22cc90795.c:128-181`). On app deactivation, the draft releases capture and stops music; activation restores focus and may reacquire capture. SDL should implement capture and focus transfer at the semantic level.

[INFERRED] Startup is single-instance: `WINMAIN` searches for class `AntRoot`, raises an existing window and returns; otherwise it registers classes only when `previousInstance == 0`, creates the frame/children, initializes the display/database/audio/options, shows intro and customer dialogs, starts a new game, builds user-button/menu state, loads cursors/accelerators, starts a timer, and enters `GetMessage`/translate/dispatch (`evidence/recovery/drafts/WINMAIN/8c89fbd1b287.c:141-257`). The entry point pairs with DOS `main` semantically, but keeps platform-specific setup (`D:/Prog/simant_recon/evidence/cross_version/simantw_correspondence.json`, `main` -> `WINMAIN`, CONFIRMED).

[INFERRED] The command path also includes a native About message box (`0xFDAB` branch); DOS menu item 1 opens `AboutDialog`. WinHelp calls provide Windows help/context handling and `CleanUp` sends WinHelp command 2 to close the help file. Preserve the DOS help content/command if in scope; WinHelp itself is optional (`evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:677-680`; `evidence/recovery/drafts/CleanUp/151a18301f6b.c:37-68`; DOS `ProcMenu` above).

[INFERRED] File selection first loads `COMMDLG.DLL` and resolves `GetOpenFileName`/`GetSaveFileName`; if unavailable, `FileSelect` falls back to Win16 `DialogBox` templates `Open`/`Save`. `OPENDLG` and `SAVEASDLG` implement directory/list selection, filename entry, and error/overwrite prompts. The RC fallback templates are 150x110 and 150x120 dialog units, captions "Load Ant Hill" and "Save As", with edit/list controls and Open/Save/Cancel buttons (`evidence/recovery/drafts/FileSelect/8c3d65cbcb3c.c:67-184`; `evidence/recovery/drafts/OPENDLG/ab57890875bc.c:36-115`; `evidence/recovery/drafts/SAVEASDLG/ac3749cedebd.c:42-174`; `src/resources/SIMANTW.RC:41-70`). SDL needs the load/save/overwrite semantics; the Win16 dialog widgets are replaceable.

[INFERRED] Quit/close is mediated by `MenuQuit`; cancelling reinstates the 17 ms timer. On accepted shutdown `CleanUp` kills and drains timer messages, destroys child HWNDs, deinstalls sound, closes WinHelp, palette and fonts, destroys the root/frame, and posts quit; after the message loop `WINMAIN` writes preferences and user-button assignments (`evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:403-433`; `evidence/recovery/drafts/CleanUp/151a18301f6b.c:37-68`; `evidence/recovery/drafts/WINMAIN/8c89fbd1b287.c:259-287`).
