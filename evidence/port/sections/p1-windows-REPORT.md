# p1-windows report: open questions for the SDL host

Status key: `[VERIFIED]` exact source/disassembly/import evidence; `[INFERRED]` draft or partial call-graph evidence; `[UNKNOWN]` unresolved.

## Questions that affect the port contract

1. **[UNKNOWN] Which resource slots are real product windows?** Win16 `win_LoadAllWindows` loops a runtime count from a resource and the storage supports 45 slots, but the inspected openers/hooks do not establish purposes for every slot. Resolve slots 6-8, 10-17, 22, 27-28, 31-33, and 37-44 from the window metadata resource or DOS resource table before defining SDL window IDs. Evidence: `win_LoadAllWindows` target `SIMTWO_MODULE:C806` / draft `evidence/recovery/drafts/win_LoadAllWindows/fcc0028f9bdb.c`; exact DOS layout in `src/root/m20E8.c:96-140`.
2. **[UNKNOWN] What are slots `0x2200` and `0x2300` in the original ownership model?** `WINMAIN` best draft assigns slot `0x2200` to the `ribbonBarWnd` child and gives it `INDEX=0x2200`; `MAINWNDPROC` draft uses `0x2200` and `0x2300` as alternative ribbon/map-data versus yard-status overlays on `WM_NCACTIVATE`. Slot `0x2300`'s class, opener, style, lifecycle, and exact ownership remain unknown. Evidence: `evidence/recovery/drafts/WINMAIN/8c89fbd1b287.c:175-190`, `evidence/recovery/drafts/MAINWNDPROC/2512b5b9e4d8.c:589-603`, plus references in DrawRibbonMessage/DrawMapData/DrawYardData.
3. **[UNKNOWN] What layout contract does SDL need to preserve on resize and display-mode changes?** `win_Recalc` is open (`SIMTWO_MODULE:E6E2`; draft `evidence/recovery/drafts/win_Recalc/868bd0db1b17.c`); `MainWndProc` draft clearly handles frame/root/ribbon and edit resizing but gives no established policy for other windows. Confirm whether portable resizing should follow the DOS anchor/layout calculations, Win16 system-frame metrics, or both. Evidence: `win_Open` draft, `win_Recalc` draft, `MAINWNDPROC` draft `:301-383`; exact DOS `win_Open` in `src/root/m20E8.c:207-255`.
4. **[UNKNOWN] Which Win16 interactions are compatibility requirements versus host artifacts?** The `MAINWNDPROC` draft connects activation to focus/capture and palette messages; `win_Open` drains selected keyboard/mouse queue messages; `win_Close` reactivates another window with `WM_NCACTIVATE`. The SDL host needs an explicit policy for modal input, mouse capture, keyboard focus, activation, and whether inactive windows continue receiving simulation input. Evidence: `MAINWNDPROC` draft `:435-603`, `win_Open` draft `:89-230`, `win_Close` draft `:28-58`, exact `win_Events` source `src/recovered/tu_simtwo_C32E_win_ObjAddr_20_reviewed-cf86811e02.c:192-210`.
5. **[UNKNOWN] Do modal dialogs need independent SDL windows?** `INDIRECTDLGPROC` draft associates a dialog HWND with a logical slot at `WM_INITDIALOG`, captures mouse input, and calls `EndDialog` on a button event, but the dialog resource/template and its normal invocation/return-value contract have not been established. Evidence: target `SIMTWO_MODULE:DDD2`, draft `evidence/recovery/drafts/INDIRECTDLGPROC/9b8767967254.c:1-43`.
6. **[VERIFIED] Is `win_IsWinExposed` an occlusion query? No.** It only tests containment in the root rectangle (`src/recovered/wf_win_IsWinExposed-22083a86a9.c:30-51`). **[UNKNOWN]** Whether callers rely on that limited meaning, or SDL should use a richer visible-region calculation, requires caller review.
7. **[UNKNOWN] What are the DOS-only candidate IDs `0x1600`, `0x1F00`, and `0x2100` in the Windows build?** These appear in DOS-side references but no corresponding Win16 opener was established in the inspected source/drafts. Determine if they were removed, folded into another window, or use dynamically selected IDs; do not reserve portable behavior based on name guesses alone. Evidence: DOS symbols/source and `evidence/cross_version/simantw_correspondence.json`; Win16 opener search remains inconclusive.
8. **[INFERRED] Should SDL reproduce OS-owned title bars/system menu and owned-window z-order?** The generic windows are created without `WS_CHILD`/`WS_POPUP`, passed `rootWnd` as `hWndParent`, receive a custom system menu, and are raised with USER z-order calls. This supports owned top-level semantics, but whether the port should implement those semantics as SDL windows or in-app panels is a product/visual decision. Evidence: `win_Open` draft `:89-230`, `win_IsWinInFront` exact source `src/recovered/win_IsWinInFront-c38b403794.c:10-31`; SDK style definitions `toolchain/sdk310/INC/WINDOWS.H:2934,2936,2978-2986,3009-3010`.

## Port-facing facts already supported

- **[VERIFIED]** Preserve the logical `ID >> 8` slot mapping and draw-hook identity; the Win16 OS window and the SimAnt logical window are distinct concepts.
- **[VERIFIED]** The Win16 frame has one top-level application HWND plus two child HWNDs (`rootWnd`, `ribbonBarWnd`); **[INFERRED]** `ribbonBarWnd` is also attached to logical slot `0x2200` by `WINMAIN`.
- **[INFERRED]** Other logical windows are created as generic windows associated with `rootWnd`.
- **[INFERRED]** Normal close behaves as hide-and-reopen/reuse, not native destruction. SDL should model logical close independently from final process shutdown.
- **[VERIFIED]** DOS is the behavioral/visual authority for game content; Win16 evidence here establishes host-specific ownership, native message flow, focus/capture, and z-order additions only.
