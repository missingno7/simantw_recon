# Consumer and initializer evidence addendum

Scope: read-only semantic analysis plus one isolated source/OMF shape comparison. This is not a `_SaveGame` or `_LoadGame` function test and did not change a job state.

## Direct consumer evidence

- The `_SaveGame` packet is `evidence/recovery/workflow/jobs/SaveGame-4535266fed/packet.md`. At function-relative `0xA3..0xC7`, it loads `0x9570`, first checks the word at `0x9572`, reads words at `[si+2]` and `[si]`, multiplies them, adds the result to a total, advances `si` by 8, then checks the next record's word at `[si+2]` for zero before looping. This directly establishes eight-byte stepping and a zero second-word loop sentinel in that pass. A second loop at `0x159..0x199` reads the words at `+6` and `+4`, computes `[si+2] * [si]`, calls the file-write import (KERNEL ordinal 86), advances by 8, and again tests the next record's `+2` word for zero.
- `_LoadGame` is represented in `evidence/disassembly/cards.jsonl` (symbol `_LoadGame`, image identity matching the provenance report). At absolute code offsets `41263..41289` (`0x18F..0x1A9` from entry `40864`), the same first pass checks the initial count at `0x9572`, multiplies `[bx+2]` by `[bx]`, adds to the total, increments by 8, and tests the next `[bx+2]` for zero. At absolute offsets `41354..41420` (`0x1EA..0x22C` from entry), its second pass checks the initial count, passes words `[si+6]` and `[si+4]`, computes `[si+2] * [si]`, calls the file-read import (KERNEL ordinal 82), advances by 8, and tests the next `+2` word for zero.
- `_SaveGame` and `_LoadGame` both use the first word and second word as multiplicative factors for per-record transfer bytes. The disassembly proves those machine-level roles; identifying the first word as an element width/kind and the second as an element count is a source-level naming inference. The `+4`/`+6` words are passed together as the far data pointer components; exact selector semantics come from NE relocation metadata, not the chain bytes.
- The observed count-zero record is at `0x9F08` (in `results.json`). The consumer code establishes a loop stop when the next record's second word is zero; that agrees with this record. The initial checks also show an empty table can be handled without processing a record. No independent evidence yet says whether a `kind==0` check is used.

## Caller and nearby source evidence

- `evidence/recovery/workflow/jobs/DoMenuEntry-3595df4ece/packet.md` shows a menu branch calling `_LoadGame` with two zero arguments at relative `0x6D` and branching on its return value.
- `evidence/recovery/workflow/jobs/NewGame-648c3dd8ca/packet.md` shows its `0x207` scenario branch calling `_LoadGame(0,0)` at relative `0x5C`; a nonzero result continues the success path. The same packet calls `_ClearLastFileName` at `0x29D` after its edit/scenario flow.
- `evidence/recovery/workflow/jobs/MenuQuit-2c1d7ca69f/packet.md` shows a confirmation path calling `_SaveGame(0)` at relative `0x2E`; the return value controls the quit path.
- `src/recovered/ClearLastFileName.c` is the adjacent recovered implementation and writes `editBufInvalidFlag[1834] = 0`. Its matched disassembly in `evidence/disassembly/cards.jsonl` stores zero to `ANTEDIT` data address `0x9520`. This establishes a cleared byte at that address and a recovered aliasing source expression, but does not identify a standalone `lastFileName` object or its size/class.
- `_SaveGame` disassembly directly checks and copies a NUL-terminated path from `0x9520` into a stack buffer before its file-selection flow (`packet.md`, relative `0x0F..0x52`). `_LoadGame` also references `0x9520` and copies path bytes (`cards.jsonl`, offsets `40961..41004`). These facts support a filename-like buffer interpretation. The 80-byte extent comes from the observed zero span and candidate shape probe, not a bound proven by either function.

## Candidate contribution comparison

Using candidate `mutable_sentinel_braced.c` / `.obj` from this folder (object SHA-256 `c70d1d05dbb1176cf04a6734ab15d4300dd5ac35265036805f33c0d706512856`; assigned `ANTEDIT_MODULE` C7 profile), I compared its 2544-byte `SIMANT_DATA_GROUP` initialized contribution with original DATA segment 8 bytes `[0x9520,0x9F10)`, under the explicit hypothesis that the contribution begins at `0x9520`.

- All 1,316 candidate bytes outside the 307 four-byte OMF far-pointer fixup spans exactly match the corresponding original bytes. This covers the 80 zero bytes, each record's first two words and terminator; no outside-fixup mismatch was found.
- All 307 candidate fixups are width-four relocations at contribution-relative offsets `80 + 8*i + 4`. Each target is the exact named MAPSYM owner recovered for the corresponding original record. In the NE image, each matching original record instead has a literal two-byte offset followed by a two-byte loader-chain relocation site. Those raw layouts cannot be compared byte-for-byte; compare the C far-pointer fixup and named target semantically against the NE relocation target plus MAPSYM offset/name.
- Thus the natural declaration can express this complete byte pattern and all record pointer targets under the hypothesized placement. It does not establish that the original compiler emitted one 2544-byte object at `0x9520`, that the filename span and table shared one declaration/TU contribution, or that the original source used these field names, pointer type, mutability, or initializer spelling. The earlier OMF result remains: mutable/const table and `{0}`/`""` filename initializers yielded identical object identity.

This improves the source-shape evidence for `_SaveGame`/`_LoadGame`, but does not independently prove object placement/ownership or make either function strictly admissible. Keep their job packets excluded from routine assignments; a later source candidate still needs its complete ordinary function strict comparison through the authorized workflow.
